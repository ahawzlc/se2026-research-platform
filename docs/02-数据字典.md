# 数据字典

本文件与 `deploy/mysql/init/01-schema.sql` 一一对应。**以本文件为口径来源**，改表先改这里。`backend/prisma/schema.prisma` 与 init SQL 的表结构、索引、外键保持一致；存量库升级用 `deploy/mysql/migrations/` 下的增量脚本，不重跑 init。

## 一、通用约定

### 命名与类型

| 项 | 约定 |
| --- | --- |
| 表名 / 字段名 | 全小写，多单词用下划线（`team_member`、`password_hash`） |
| 主键 | 统一 `id BIGINT UNSIGNED AUTO_INCREMENT` |
| 字符集 | `utf8mb4` / `utf8mb4_unicode_ci` |
| 存储引擎 | InnoDB |
| 金额/权重 | `DECIMAL`，不用浮点 |
| 枚举字段 | 用 `VARCHAR` 存字符串字面量（可读性优先），取值在建表注释中列明 |

### 每张表都带的公共字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键，自增 |
| `created_at` | DATETIME | 创建时间，默认当前时间 |
| `updated_at` | DATETIME | 更新时间，更新自动刷新 |
| `deleted` | TINYINT UNSIGNED | 逻辑删除：`0` 正常，`1` 已删除 |

例外：`activity_log` 为**只增不改**的行为流水，仅保留 `created_at`，不含 `updated_at` 与 `deleted`。

> **逻辑删除的注意事项**
> 逻辑删除后记录仍占位，会影响唯一索引。例如 `user.username` 加了唯一索引后，已删除用户的用户名无法再被注册。第一版接受该限制并在昵称/用户名上给出「已被占用」提示；若后期需要释放，可把唯一索引改为 `(username, deleted)` 组合索引，或引入 `deleted_at` 时间戳参与唯一键。

### 外键约束（2026-11-03 起 28 个；2026-11-20 卡 G-0 新增 10 个，共 38 个）

早期版本刻意不建外键（逻辑删除在应用层控制）。2026-11-03 起与 `backend/prisma/schema.prisma` 对齐补齐外键：**外键只兜底物理孤儿行**，逻辑删除语义不变，仍由应用层控制。约束名统一 `<表>_<列>_fkey`；删除规则两类：普通列 `RESTRICT`（引用行还在就不许物理删父行），可空引用列 `SET NULL`（父行物理删除时置空）；更新规则一律 `CASCADE`。

| 引用方.列 → 被引用方 | ON DELETE |
| --- | --- |
| `team.owner_id` → `user` | RESTRICT |
| `team_member.team_id` → `team`、`team_member.user_id` → `user` | RESTRICT |
| `file.uploader_id` → `user` | RESTRICT |
| `project.team_id` → `team` | RESTRICT |
| `project_member.project_id` → `project`、`project_member.user_id` → `user` | RESTRICT |
| `milestone.project_id` → `project` | RESTRICT |
| `task.project_id` → `project` | RESTRICT |
| `task.assignee_id` → `user`（可空） | SET NULL |
| `literature.team_id` → `team`、`literature.uploader_id` → `user` | RESTRICT |
| `literature.project_id` → `project`（可空）、`literature.file_id` → `file`（可空） | SET NULL |
| `literature_tag.literature_id` → `literature` | RESTRICT |
| `meeting.project_id` → `project` | RESTRICT |
| `meeting_attendee.meeting_id` → `meeting`、`meeting_attendee.user_id` → `user` | RESTRICT |
| `achievement.project_id` → `project` | RESTRICT |
| `achievement.file_id` → `file`（可空） | SET NULL |
| `achievement_member.achievement_id` → `achievement`、`achievement_member.user_id` → `user` | RESTRICT |
| `conversation_member.conversation_id` → `conversation`、`conversation_member.user_id` → `user` | RESTRICT |
| `message.conversation_id` → `conversation`、`message.sender_id` → `user` | RESTRICT |
| `activity_log.team_id` → `team`、`activity_log.user_id` → `user` | RESTRICT |

| `community_post_tag.post_id` → `community_post`、`community_post_tag.tag_id` → `community_tag` | RESTRICT |

存量库（含生产）补齐外键用 `deploy/mysql/migrations/20261103-01-add-fk.sql`（先跑脚本内的孤儿行检查）。

### meeting 会议

| 字段 | 类型 | 允许空 | 说明 |
| --- | --- | --- | --- |
| `project_id` | BIGINT UNSIGNED | 否 | `project.id` |
| `title` | VARCHAR(200) | 否 | 会议主题 |
| `held_at` | DATETIME | 是 | 召开时间 |
| `location` | VARCHAR(200) | 是 | 地点或线上会议链接 |
| `content` | LONGTEXT | 是 | 会议记录正文 |

索引：`idx_meeting_project (project_id, held_at)`。

F-2 的 `status` **不是数据库列**：API 根据 `held_at`（UTC）与服务端当前时间推导；空值为 `unscheduled`，`held_at > now` 为 `upcoming`，`held_at <= now < held_at+120min` 为 `ongoing`，满 120 分钟为 `ended`。会议表没有结束时间，120 分钟是默认估算时长。对外 `heldAt` 统一格式化为北京时间。无需修改 DDL、Prisma 或执行迁移。

提醒每分钟扫描 `[now, now+60min]` 的有效会议及有效参会人，排除已删项目；通知写入现有 `notification` 表，以 `meeting_upcoming / meeting / 会议 id` 标识来源。

## 四、沟通类

三张表构成统一会话模型：**上下文评论、项目讨论区、成员私信共用同一套结构**，仅以 `type` 区分。

| `type` | 语义 | `ref_type` / `ref_id` |
| --- | --- | --- |
| `comment` | 锚定在业务对象上的评论 | 指向 `task` / `achievement` / `meeting` 等 |
| `group` | 项目讨论区 | 指向 `project` |
| `private` | 成员私信 | 为空 |
| `meeting` | 会议讨论区（F-1，2026-11-20 起） | 指向 `meeting` |

### conversation 会话

| 字段 | 类型 | 允许空 | 说明 |
| --- | --- | --- | --- |
| `type` | VARCHAR(20) | 否 | `comment` / `group` / `private` / `meeting` |
| `ref_type` | VARCHAR(30) | 是 | 业务对象类型，私信为空 |
| `ref_id` | BIGINT UNSIGNED | 是 | 业务对象主键，私信为空 |
| `title` | VARCHAR(200) | 是 | 会话标题（群组用） |

索引：`idx_conversation_ref (ref_type, ref_id)`。

### conversation_member 会话成员与已读位点

| 字段 | 类型 | 允许空 | 说明 |
| --- | --- | --- | --- |
| `conversation_id` | BIGINT UNSIGNED | 否 | `conversation.id` |
| `user_id` | BIGINT UNSIGNED | 否 | `user.id` |
| `last_read_at` | DATETIME | 是 | 最后已读时间，**未读数的唯一依据** |

索引：唯一 `uk_conversation_member (conversation_id, user_id)`；`idx_cm_user (user_id)`。

> **未读数算法**：`未读数 = COUNT(message WHERE conversation_id = ? AND created_at > last_read_at)`。
> 该设计只需一条查询语句，不为每条消息维护已读状态；见实现方案第五条要点。

## 五、统计类

### activity_log 行为埋点流水

**贡献度分析的唯一数据来源。** 任何写入业务数据的动作都应在同一事务内追加一条记录。

| 字段 | 类型 | 允许空 | 说明 |
| --- | --- | --- | --- |
| `user_id` | BIGINT UNSIGNED | 否 | 行为人 |
| `team_id` | BIGINT UNSIGNED | 否 | 归属课题组（统计口径以团队为单位） |
| `type` | VARCHAR(40) | 否 | 行为类型，见下表 |
| `ref_type` | VARCHAR(30) | 是 | 关联对象类型 |
| `ref_id` | BIGINT UNSIGNED | 是 | 关联对象主键，用于**去重**（同一对象重复行为可识别） |
| `weight` | DECIMAL(5,2) | 否 | 该行为的基础权重，默认 `1.00`，最终口径见 03 号文档 |
| `created_at` | DATETIME | 否 | 发生时间，默认当前时间 |

索引：`idx_log_team_user_time (team_id, user_id, created_at)`；`idx_log_team_type (team_id, type)`；`idx_log_user_time (user_id, created_at)`。

`type` 建议取值：

| 取值 | 触发场景 |
| --- | --- |
| `task_create` | 新建任务 |
| `task_done` | 完成任务 |
| `comment_create` | 在业务对象下发表评论 |
| `literature_upload` | 上传文献 |
| `literature_read` | 标记文献已读 |
| `meeting_create` | 创建会议记录 |
| `meeting_attend` | 参加会议 |
| `achievement_submit` | 登记成果 |
| `milestone_done` | 完成里程碑 |

> **`ref_id` 是反刷分的关键**：统计时可对同一 `(type, ref_id)` 的行为去重或做衰减，避免用重复点击刷高分数。

| `note` | VARCHAR(200) | 否 | 申请说明，默认空串 |
| `status` | VARCHAR(20) | 否 | `pending` / `approved` / `rejected` |
| `handled_by` | BIGINT UNSIGNED | 是 | 处理人（发帖人）`user.id` |
| `handled_at` | DATETIME | 是 | 处理时间 |

索引：唯一 `uk_team_application (post_id, user_id)`；`idx_team_application_user (user_id)`；`team_application_handled_by_fkey (handled_by)`。

### friendship 好友关系

**单向行表示一条关系**（A→B 与 B→A 是两行）；查询好友列表时按 requester/addressee 双向取。被拒后可再次发起：**复用同一行改回 `pending`**（唯一键占位，不能删除重插——逻辑删除占位的限制同 user.username）。

| 字段 | 类型 | 允许空 | 说明 |
| --- | --- | --- | --- |
| `requester_id` | BIGINT UNSIGNED | 否 | 发起方 `user.id` |
| `addressee_id` | BIGINT UNSIGNED | 否 | 接收方 `user.id` |
| `status` | VARCHAR(20) | 否 | `pending` 待同意 / `accepted` 已互为好友 / `rejected` 已拒绝 |
| `handled_at` | DATETIME | 是 | 处理时间 |

索引：唯一 `uk_friendship (requester_id, addressee_id)`；`idx_friendship_addressee (addressee_id)`。

### notification 站内通知

唯一写入口是 G-1 的 `NotificationService.push`，其他模块不得直写本表。

| 字段 | 类型 | 允许空 | 说明 |
| --- | --- | --- | --- |
| `user_id` | BIGINT UNSIGNED | 否 | 接收人 `user.id` |
| `type` | VARCHAR(30) | 否 | `team_apply` / `team_apply_approved` / `team_apply_rejected` / `friend_request` / `friend_accepted` / `meeting_upcoming`（F-2 会前提醒） |
| `title` | VARCHAR(200) | 否 | 通知标题（列表直显） |
| `ref_type` | VARCHAR(30) | 是 | 跳转来源对象类型（`community_post` / `friendship` / `meeting` / `conversation`），多态引用不建外键 |
| `ref_id` | BIGINT UNSIGNED | 是 | 跳转来源对象主键 |
| `is_read` | TINYINT UNSIGNED | 否 | 0 未读 / 1 已读 |

索引：`idx_notification_user_read (user_id, is_read)`（铃铛角标+列表）；`idx_notification_dedupe (user_id, type, ref_id)`（F-2 会前提醒幂等判重）。

F-2 顺序扫描按 `(user_id, type, ref_type, ref_id, deleted=0)` 查重，已读通知仍参与去重。`idx_notification_dedupe` 是普通索引，不是唯一约束；现方案面向单实例，不保证多实例并发严格去重，不改变冻结的 `push` 接口。
