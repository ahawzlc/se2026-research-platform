-# 接口规范

本文件为前后端共同遵守的接口约定。前端封装（`frontend/src/api/request.ts`）已按本规范实现，后端请对齐同样的返回结构，否则前端需额外适配。

## 一、基本约定

| 项 | 约定 |
| --- | --- |
| 接口前缀 | `/api/v1` |
| 风格 | RESTful，用 HTTP 方法表达动作 |
| 请求/响应体 | `application/json`，文件上传除外（`multipart/form-data`） |
| JSON 字段命名 | 小驼峰（`createdAt`、`assigneeId`） |
| **主键与 id 字段** | 一律以**字符串**传输（后端 BIGINT 主键序列化为字符串），前端不要当数字做运算；详见 [06-环境终检报告.md](06-环境终检报告.md) |
| URL 路径命名 | 全小写，多单词用中划线（`/literature-tags`） |
| 时间格式 | `yyyy-MM-dd HH:mm:ss`（北京时间，后端用 `src/common/datetime.ts` 的 `formatDateTime()`）；仅日期字段用 `yyyy-MM-dd`（用 `formatDate()`）。**数据库内统一存 UTC** |
| 字符集 | UTF-8 |

## 二、统一返回体

所有接口（含错误）都返回同一结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | int | 业务状态码，`0` 表示成功，非 0 表示失败 |
| `message` | string | 提示信息，成功时为 `ok`，失败时为可直接展示给用户的文案 |
| `data` | any | 数据体，失败时为 `null` |

### 业务状态码

| code | 含义 | 前端处理 |
| --- | --- | --- |
| `0` | 成功 | 取 `data` 使用 |
| `400` | 参数校验失败 | 提示 `message` |
| `401` | 未登录 / 令牌失效 | 清除本地令牌并跳转登录页 |
| `403` | 已登录但无权限 | 提示无权限，不做跳转 |
| `404` | 资源不存在 | 提示并返回列表页 |
| `409` | 状态冲突（如邀请码重复、重复入组） | 提示 `message` |
| `500` | 服务端异常 | 提示「服务异常，请稍后重试」 |

HTTP 状态码仍按语义返回（成功 200、未授权 401 等），但**前端以业务 `code` 为准**，不依赖 HTTP 状态码判断成败。

## 三、鉴权

- 需要登录的接口在请求头携带令牌：

```
Authorization: Bearer <token>
```

- 令牌由登录接口签发，前端持久化在 `localStorage`，由 Axios 请求拦截器自动注入；
- 令牌失效返回 `code: 401`，前端响应拦截器统一处理为「清令牌 + 跳登录」；
- **所有涉及课题组数据的查询，后端都必须附加团队标识条件**，防止越权访问他人数据。

## 四、分页

列表接口统一使用 `page` 与 `size` 两个查询参数：

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `page` | int | 1 | 页码，**从 1 开始** |
| `size` | int | 10 | 每页条数，服务端限制上限 100 |

分页响应统一结构（放在 `data` 中）：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "list": [],
    "total": 0,
    "page": 1,
    "size": 10
  }
}
```

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/auth/register` | 注册，入参 `username`、`password`、`nickname`、`email`（email 可选：不填或空串均视为未提供，落库存空串；非法格式仍 400） |

> **限流（2026-11-19 起）**：`register` / `login` 受内存滑动窗口限流——单 IP 每分钟 20 次（两接口合计）、

> 「尝试过于频繁，请 1 分钟后再试」。单实例内存实现，重启即清零，见 `backend/src/auth/`。

### 协作沟通

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/conversations` | 会话列表（含未读数，按最近活动倒序；可按 `type` 过滤） |
| POST | `/api/v1/conversations/group` | 创建/获取项目讨论区（一个项目一个群组会话；入参 `projectId`） |
| POST | `/api/v1/conversations/private` | 创建/获取私信会话（入参 `peerUserId`，双方须在同一课题组） |
| GET | `/api/v1/conversations/{id}` | 会话详情（含未读数） |
| GET | `/api/v1/conversations/{id}/messages` | 会话消息列表（按时间正序，`limit` 默认 50、1–200） |
| POST | `/api/v1/conversations/{id}/messages` | 发送消息（入参 `content`，1–2000 字符） |
| GET | `/api/v1/conversations/unread` | 未读消息汇总（**前端 30s 轮询**） |
| POST | `/api/v1/conversations/{id}/read` | 标记会话已读（推进 `lastReadAt`） |

> **消息埋点口径**：消息（`message`）**不产生任何埋点**，不计入参与度（`docs/03` 红线 1）。
> 私信属私人沟通，统计会侵犯隐私并诱导行为变形；项目讨论区消息条数同样不计入。
>
> **轮询间隔**：以 SRS 为准采用 **30 秒**；`docs/01` 旧版 3–5 秒为存量冲突，已废弃。
>
> **会话 title 口径**：`group` 为项目名（共享）；`comment` 为锚定对象标题（共享）；
> `private` 建会话时 title 列为空，接口返回时按**查看者**解析为对方昵称（每人视角不同）。
> 讨论区成员按需加入：各自进入讨论区后才会出现在自己的会话列表。
>
> **未读数算法**：`未读数 = COUNT(message WHERE conversation_id = ? AND created_at > last_read_at)`；
> 发送消息时自动把发送者的 `last_read_at` 推进到当前时间，避免自己给自己算未读。

### 通知中心

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/notifications` | 我的通知列表（分页，`unreadOnly=true` 仅看未读，按 id 倒序） |
| GET | `/api/v1/notifications/unread-count` | 未读数（**顶栏铃铛 30s 轮询**，与消息页未读各自独立） |
| POST | `/api/v1/notifications/{id}/read` | 单条已读（幂等；非本人通知与不存在同口径 404） |
| POST | `/api/v1/notifications/read-all` | 全部已读（返回 `updated`：本次标记条数） |

> **写入唯一入口**：通知由服务端 `NotificationService.push({ toUserId, type, title, refType?, refId? })` 产生
> （组队申请/审批、好友申请/通过、会前提醒），**不开放 HTTP 写接口**；幂等由调用方保证。
> 已读取值用 POST（与会话已读一致，前端 http 封装暂无 PATCH）。
>
> `type` 取值：`team_apply / team_apply_approved / team_apply_rejected / friend_request /
> friend_accepted / meeting_upcoming`（末项为 F-2 会前提醒占位）。新增类型需同步
> docs/02 表注释与 `backend/src/notifications/notification.constants.ts`。
>
> `refType` / `refId` 为跳转来源（`community_post / friendship / meeting / conversation`），
> 多态引用不建外键；两者同进同退，缺省时均为空串/空。前端按已知来源路由跳转，未知来源仅标记已读。
>
> 通知是**个人维度**资源（平台第一个无团队归属的模块）：service 层仅按本人 `userId` 过滤；
> 消息未读仍走消息页既有机制，不进铃铛（铃铛=事件通知，消息页=会话）。

### 组队广场

线②（卡 E-1 帖子与标签 / 卡 E-2 申请与审批）。表结构见 docs/02 第七节的四张 `community_*` / `team_application` 表。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/community/posts` | 发布招募帖（`title`、`tagIds` 必填；可传 `content`、`recruitTotal`），返回帖子结构 |
| GET | `/api/v1/community/posts` | 广场列表（分页，按 id 倒序；可按 `tags`、`q`、`status`、`mine` 过滤），`list` 每项为帖子结构 |
| GET | `/api/v1/community/posts/{id}` | 帖子详情（含发布人卡片、标签、招募进度） |
| PUT | `/api/v1/community/posts/{id}` | 编辑帖子（仅发帖人；仅「招募中」可编辑；字段同发布且均可选，至少传一个） |
| POST | `/api/v1/community/posts/{id}/close` | 停止招募（仅发帖人；转「已停止」，不可逆） |
| DELETE | `/api/v1/community/posts/{id}` | 删除帖子（仅发帖人；逻辑删除，已组建的课题组不受影响；**还有待处理申请时 409**） |
| GET | `/api/v1/community/tags` | 标签字典（按类别、id 排序；新增标签走 Issue 流程，不开放写接口） |
| POST | `/api/v1/community/posts/{id}/apply` | 申请加入（入参 `note` ≤200 字符，可省略）；仅「招募中」且非本人帖子，每人每帖至多一条申请 |
| GET | `/api/v1/community/posts/{id}/applications` | 该帖的申请列表（分页，按 id 倒序；仅发帖人；可按 `status` 过滤） |
| POST | `/api/v1/community/applications/{id}/approve` | 通过申请（仅发帖人）：自动建组、入组、进度 +1（申请人已在课题组内的不占名额），招满转「已满员」，并通知申请人 |
| POST | `/api/v1/community/applications/{id}/reject` | 拒绝申请（仅发帖人），并通知申请人 |

> **发帖字段**：`title` 1–50 字符；`content` 纯文本 ≤5000 字符，可省略；`tagIds` 为字典 id 数组，
> **必选 1–3 个且不可重复**（DTO 拦截），含字典外的 id → 400；`recruitTotal` 取 1–10，默认 1。
> 编辑时 `recruitTotal` 不得小于等于 `recruitedCount`（至少留 1 个名额，否则 400）。
>
> **状态机**：`recruiting` 招募中（发布默认）→ `full` 已满员（审批通过后招满自动转入，E-2）；
> `recruiting` / `full` → `closed` 已停止（发帖人主动停止）。`closed` 为终态；
> 非 `recruiting` 时编辑、已 `closed` 时再停止均返回 409。
>
> **帖子结构**（发布、编辑、列表项、详情同构）：
> `id / title / content / recruitTotal / recruitedCount / status /
> tags[{ id, name, category }] / author{ id, nickname, avatar } / team{ id, name } | null /
> isAuthor / myApplication / pendingCount / createdAt / updatedAt`。
> `author` 只给昵称与头像，不暴露登录名与邮箱（社区是跨组公开内容）；
> `team` 为审批通过后绑定的课题组（E-2），未绑定为 `null`；`isAuthor` 表示当前用户是否发帖人；
> `myApplication` 为**当前用户在该帖的申请** `{ id, status, note, createdAt, handledAt }`，未申请为 `null`；
> `pendingCount` 为待处理申请数，**仅发帖人有意义**，其他人恒为 0。
>
> **申请与审批（卡 E-2）**——申请状态机 `pending → approved / rejected`，**不可逆**；
> 被拒后不可再申请同帖（`uk_team_application(post_id, user_id)` 唯一键 + service 层状态校验双保险）。
>
> - **申请**：帖子已满员 / 已停止 → 409；申请自己的帖子 → 400；已有申请（任何状态）→ 409，不产生第二条；
>   已在该帖绑定的课题组内（如凭邀请码先入组）→ 409「你已在该课题组中，无需申请」（否则通过时进度会多计一人）。
> - **审批**：非发帖人 403；申请不存在 404；申请已处理 → 409；帖子已满员再通过 → 409
>   （申请人**已是该帖课题组成员**的存量申请除外，见下面「进度只计经审批入组的人」）。
>   已停止的帖子仍可处理**存量**待处理申请（名额内），处理完仍保持「已停止」。
> - **通过是原子的**：同一事务内依次完成「申请置为 approved → 锁定帖子行并回读（名额与课题组绑定
>   以持锁后已提交的数据为准，同一帖子的并发审批在此排队）→ 帖子尚未绑定课题组则自动创建
>   （名称 = 帖子标题，发帖人为组长）→ 申请人写入课题组成员 → 名额条件更新（仅当
>   `recruited_count < recruit_total` 才 +1，并发下不会超招）→ 达到招募人数转 `full` → 写通知」，
>   任一步失败整体回滚。申请人若曾退出该组，恢复原成员行而不是新增（同 `POST /teams/join`）。
> - **进度只计「经审批入组」的人**：申请人提交申请之后、被通过之前已凭邀请码入组的（先申请、后入组），
>   发帖人仍可通过这条申请，但帖子不变——`recruitedCount` 不 +1、不转「已满员」，帖子已满员时也照常通过；
>   申请置为 approved，通知照发。它与申请入口的 409 是同一条口径的两端。
> - **审批响应**：`{ application, post{ recruitedCount, recruitTotal, status, team }, inviteCode? }`；
>   `inviteCode` **仅在本次审批自动创建课题组时返回**（邀请码只在创建时给出一次，与 `POST /teams` 同口径），
>   供组长线下拉人使用。
> - **申请条目**：`id / postId / status / note / createdAt / handledAt / applicant{ id, nickname, avatar }`。
> - **删除帖子**：还有 `pending` 申请时返回 409（提示先处理），避免申请人的申请随帖子一起变得无处可查、
>   永远等不到结果；只想停止接新申请请用「停止招募」。
>
> **通知**（调 `NotificationService`，铃铛与通知页可点跳帖子详情）：申请人 → 发帖人 `team_apply`
> 「{申请人昵称} 申请加入你的帖子《{帖子标题}》」；通过 → 申请人 `team_apply_approved`
> 「{发帖人昵称} 通过了你加入《{帖子标题}》的申请」；拒绝 → 申请人 `team_apply_rejected`
> 「{发帖人昵称} 拒绝了你加入《{帖子标题}》的申请」。三类 `refType` 均为 `community_post`。
> 申请与审批**同样不写 `activity_log`**（理由同发帖：发生在课题组之外，无法归属到团队）。
>
> **筛选**：`tags` 逗号分隔的标签 id，命中任一即返回；`q` 匹配标题或正文；`status` 取
> `recruiting / full / closed`，省略为全部状态（已停止的帖子仍在广场可见，带状态徽章）；
> `mine=true` 只看我发布的。已删除的帖子在列表与详情中均不可见（详情按 404 处理）。
>
> **权限**：广场对全站登录用户可见；编辑、停止、删除仅发帖人可操作，非发帖人 403；
> 帖子不存在、已删除或 id 非法一律 404。
>
> **与 docs/12 接口方向的三处出入**（实现口径以本节为准）：
> ① 编辑用 `PUT` 而非 `PATCH`——前端 `http` 封装无 PATCH，且项目/文献/会议的更新接口均为 PUT；
> ② 筛选参数为 `tags`（可多值）而非 `tag`——任务卡要求「标签多选」；
> ③ 补 `POST /posts/{id}/close` 与 `mine`——任务卡要求「停止招募」与「管理自己的帖子」，原接口方向未列出。
>
> 另有两处口径是任务卡未写明、实现时定下的，**请评审时确认**：删帖受「有待处理申请则 409」约束；
> 审批只发 1 条通知（给申请人），任务卡写的「发 2 条通知」未指明第二条给谁。
>
> **埋点**：社区帖子**不写 `activity_log`**。`activity_log.team_id` 非空且参与度统计以团队为单位，
> 而发帖发生在任何课题组之外（`community_post.team_id` 发帖时为空），现有表结构下无法归属；
> 任务卡提到的 `post_create` 类型待全组确认口径后再定（见 docs/16）。

## 七、D-1 统计契约

两个接口均需 JWT 与当前团队成员身份；teamId 为必填正整数字符串（BIGINT UNSIGNED 范围），details 可选 userId 同规则、dimension 取 task/achievement/milestone/meeting/literature/discussion。禁止额外参数。分页 page 默认 1、size 默认 10，上限 100。可选 weekStart 为有效的北京时间周一（yyyy-MM-dd）。

汇总 data：teamId、memberCount（有效团队成员数）、modelVersion、disclaimer、sampleSize（有效事件数）、sampleThreshold、insufficientSample、hasData、dimensions（key/label/weight/max）、members（userId/nickname/hasData/index[0–1 或 null]/dimensions[key/raw/normalized]）、weekly（weekStart/count/weight）。不按指数排序，成员按 userId 排序。空样本返回空 members/weekly，不展示确定的 0 分。

明细 data 为标准 list/total/page/size；每条含 id/userId/type/refType/refId/createdAt（北京时间）、originalWeight、countedWeight、counted、reason（counted/unknown_type/invalid_ref/revoked/duplicate/inactive_task/invalid_comment/daily_limit）。最新记录在前。成员与维度筛选可提前缩小读取范围，周筛选和分页在全历史去重、限额之后执行。source 为当前仍可访问的关联对象（kind/id/title/projectId），缺失、已删除或组外对象返回 null。评论仅关联同组任务，响应不返回评论正文。明细仅包含当前有效成员的日志。

模型、时间和限制见 docs/03 第九节。summary 的 weekly 即 D-1 周趋势数据源。两个 GET 接口只读，不产生埋点。
