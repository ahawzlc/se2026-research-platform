# 贡献度（成员参与度）口径说明

本文件是贡献度分析模块的**口径来源**，也是答辩时的统一说法。实现（D 组）与展示文案（前端）都必须与本文件一致。

## 一、定位声明（最重要的一段）

> 本模块输出的是**团队协作过程的可视化参考**，反映成员在平台内留下的协作行为痕迹，**不构成任何形式的科研贡献评价**，也不作为绩效、署名顺序或考核依据。

同时必须避免的口径表述：

| 不要说 | 应该说 |
| --- | --- |
| 贡献度得分 / 贡献排名 | 参与度画像 / 活跃度分布 |
| 谁贡献最大 | 谁在平台内的协作行为更密集 |
| 贡献度考核 | 过程可视化，仅供参考 |

在界面、文档、答辩 PPT 中，一律使用「参与度」「活跃度」「协作画像」等词，**不出现「贡献度」作为评价性表述**（内部代码标识符不受此限）。

## 二、数据来源

唯一数据来源是 `activity_log` 表（见 [02-数据字典.md](02-数据字典.md)）：

- 任何写入业务数据的动作，都要在同一事务内追加一条埋点记录；
- 埋点必须**从第 1 周就随基础模块一起实现**，否则后期无历史数据可统计；
- 每条记录携带 `user_id`、`team_id`、`type`、`ref_type`、`ref_id`、`weight`、`created_at`；
- `ref_id` 用于识别「同一对象的重复行为」，是反刷分的基础。

## 三、维度划分

| 维度 | 计入的行为类型（`activity_log.type`） | 权重建议 | 依据 |
| --- | --- | --- | --- |
| 任务推进 | `task_create`、`task_done` | 3.0 | 直接推动项目进度，是最核心的产出性行为 |
| 成果沉淀 | `achievement_submit` | 3.0 | 团队最终交付物 |
| 里程碑达成 | `milestone_done` | 2.5 | 阶段性目标完成 |
| 会议参与 | `meeting_create`、`meeting_attend` | 1.5 | 过程性投入，成本低，权重下调 |
| 文献工作 | `literature_upload`、`literature_read` | 1.0 | 辅助性投入 |
| 讨论互动 | `comment_create` | 0.5 | 沟通成本最低、最易刷，故权重最低 |

> 权重是**初始建议值**，第一版先按此实现，D 组需在第 6–7 周拿到真实埋点数据后校准一次，并把校准前后的对比写进答辩材料——这本身就是有说服力的分析过程。

## 四、计算方式

分三步，全部可解释：

1. **维度内聚合**：某成员在某维度上的原始值 = 该维度内所有行为 `weight` 之和（经过第 6 节的去重与上限约束）。
2. **归一化**：对某一维度，取团队内最大值做归一化，得到 `0–1` 区间：
   `归一化值 = 本人原始值 / 团队该维度最大值`（最大值为 0 时该维度整体记 0）。
3. **加权汇总**：`综合参与指数 = Σ(维度权重 × 归一化值) / Σ(维度权重)`，结果落在 `0–1`，展示时乘以 100。

归一化而非直接求和的目的：避免「干活多的人把尺度拉爆」，让团队成员在同一量纲上可比。

## 五、明确排除的内容

以下内容**一律不计入**，理由是易刷、且会诱导行为变形：

1. **私信（`conversation.type = private`）不纳入任何统计**。私信是私人沟通，统计它既侵犯隐私又会诱导「为刷分而私聊」；
2. **不以消息条数作为指标**。发消息是最低成本动作，机械灌水会立刻使数据失真。讨论互动维度只统计**锚定在业务对象上的评论**（`comment` 类型），且权重仅 0.5，作为弱信号；
3. **不统计登录次数、页面停留等被动行为**。这类数据无法反映实质投入，且采集成本高；
4. **不统计成员自述的贡献说明**（`achievement_member.contribution_note`），该字段仅用于展示，不参与计算。

## 六、反刷分设计

必须在实现中体现，也是答辩提问的高频落点：

1. **同对象去重**：同一 `(type, ref_type, ref_id)` 的行为，同一成员只计一次（如反复把同一任务标记完成只算一次）；
2. **单位时间上限**：同一成员同一 `type` 在单日内计入次数设上限（建议评论类 10 次/日、文献类 5 次/日），超出部分不再累计；
3. **反向行为扣减**：任务从 `done` 退回 `doing` 时，撤销对应的 `task_done` 计入（或记负向流水）；
4. **权重集中管理**：权重写在配置文件或常量表中，不散落在业务代码里，便于校准与答辩演示；
5. **口径可追溯**：界面上的每个数值都能下钻到具体的行为流水，答辩时可现场点开明细自证。

## 七、展示形式

| 形式 | 内容 | 说明 |
| --- | --- | --- |
| 雷达图 | 各维度归一化值 | 直观展示成员的投入结构差异 |
| 横向排行 | 综合参与指数 | **仅展示分布，标注「仅供参考」** |
| 趋势折线 | 按周聚合的活跃度 | 反映投入的时间分布 |
| 明细下钻 | 行为流水列表 | 可追溯到具体对象，支撑答辩自证 |

所有图表必须附带固定说明文案：

> 本图表反映成员在平台内的协作行为分布，仅作团队过程参考，不构成科研贡献评价。

## 八、答辩预设问答

| 可能被问 | 回答要点 |
| --- | --- |
| 凭什么这么算权重？ | 权重依据行为的「成本 × 对项目的推进度」排序，先取经验初值，再用第 6–7 周的真实数据校准，校准过程有记录 |
| 能不能刷分？ | 有三层约束：同对象去重、单日上限、反向扣减；且最高权重的行为（完成任务、登记成果）都需要真实写入业务数据，代价高 |
| 为什么不计私信？ | 私信属私人沟通，统计会侵犯隐私并诱导行为变形；我们只统计锚定业务对象的公开协作 |
| 这个分数能不能用来评价人？ | 不能。它是过程可视化，不是评价工具，我们在界面和文档中都做了明确标注 |
| 数据量少会不会失真？ | 会。所以第一版只做「分布展示」，不做绝对判断；数据不足时界面会给出样本量提示 |
