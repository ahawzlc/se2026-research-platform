## 四、发现并已修复的隐患（3 处）

### 隐患 1：Prisma 的 BigInt 主键会让所有查询接口 500 ⚠️ 高

`BIGINT UNSIGNED` 主键在 Prisma 里是 JS `BigInt`，而 `JSON.stringify` **无法序列化 BigInt**，实测报
`TypeError: Do not know how to serialize a BigInt`。也就是说组员写的**第一个返回实体的接口就会 500**。

**修复**：新增 `backend/src/common/bigint.ts`，启动时给 `BigInt.prototype.toJSON` 打补丁，统一序列化为**字符串**
（与 JWT 载荷里的 `sub` 一致，且不丢精度）。配套单测 `bigint.spec.ts`（4 项）。

### 隐患 2：CORS 通配来源 + 携带凭证会被浏览器拒绝

原配置 `origin: '*'` 与 `credentials: true` 同时存在，浏览器规范禁止该组合，直连调试时会报错。

**修复**：`origin` 为 `*` 时自动关闭 `credentials`。实测响应头只剩 `Access-Control-Allow-Origin: *`，不再带
`Access-Control-Allow-Credentials`。

### 隐患 3：id 类型前后端不一致 + 时间格式/时区

1. **id 类型**：后端序列化后 id 是字符串，而前端 `types.ts` 声明的是 `number` → 已改为 `string`，并在
   `docs/01-接口规范.md` 增加「主键与 id 字段一律以字符串传输」的约定；
2. **时间格式**：规范要求 `yyyy-MM-dd HH:mm:ss`（北京时间），但 Nest/Prisma 默认吐 ISO 8601 → 新增
   `backend/src/common/datetime.ts`（`formatDateTime` / `formatDate` / `toIdString`），业务模块一行调用即可，
   配套单测 7 项；
3. **时区**：Prisma 读 MySQL `DATETIME` 时**一律按 UTC 解释**，而原 compose 把 MySQL 设为
   `--default-time-zone=+08:00`，两者叠加会让时间整体差 8 小时 → 已将 compose 改为**统一按 UTC 存储**
   （`+00:00`），对外展示由 `formatDateTime()` 转北京时间。

### 隐患 4：`localhost` 被 Prisma 解析为 IPv6 导致连不上 MySQL ⚠️ 高

（2026-10-15 启动 Docker 实测时发现）后端 `.env` 的 `DATABASE_URL` 原来写 `@localhost:3306`，
在 Windows + Docker Desktop 环境下，Prisma 引擎把 `localhost` 解析为 IPv6 `::1`，而容器的
3306 端口在 IPv6 转发链路上不可达，导致 `PrismaService` 启动时报
`Can't reach database server at localhost:3306` / `Server has closed the connection`。

**修复**：`backend/.env` 与 `backend/.env.example` 的 `DATABASE_URL` 主机名统一改为
`127.0.0.1`（明确走 IPv4），并更新注释说明（容器内运行仍用服务名 `mysql`）。实测
`127.0.0.1` 可正常 `$connect`，`localhost` 必失败。
