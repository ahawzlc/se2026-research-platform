## 排坑两则（Issue #42 修复过程中发现，全组适用）

1. **拉取 G-0 之后本地必须跑一次 `npx prisma generate`**（backend 目录内）：`npm ci` 的 postinstall 只在装依赖时生成 Client，之后加的 `notification` 等模型本地不可见——现象是 eslint 报一片"Unsafe member access on a type that could not be resolved"、而 CI（每次 npm ci 重新 generate）完全正常。本地 `npm test` 因 mock 转换能过，极具迷惑性；
2. **不要用 `npm run lint | tail` 判断 lint 结果**：管道会让退出码变成 tail 的 0，连续两次假绿（含 AI 本次）。正确姿势：`npm run lint; echo $?` 或 `set -o pipefail`。

## ssh askpass 通道使用备忘（更新真库验证环境结论）

- **可用**：短命令（如 `echo`、`ls`、单条 `docker exec -i ... < 服务器上的文件`——迁移就是这么跑的）；
- **不可用**：本地 stdin 管道进 ssh、超长命令串（base64 载荷）、`docker exec`（无 -i）+ `-e` 多语句查询、heredoc+docker 组合——表现为无输出挂起；
- 结论：**需要真库的一切验证走 GH Actions（schema-verify 模式）**；生产运维操作拆成最小短命令逐条执行。
- **2026-11-26 补充**：上面「超长命令串（base64 载荷）不可用」要拆开看——单条命令 250–600 字节都正常；base64 切成 200 字符左右、每段一条命令，就能把几 KB 的文件搬上服务器（做法见下一节）；`docker exec -e MYSQL_PWD=…` 接单条 `-e` 查询也正常。

## 生产库迁移执行记录（2026-11-26，线③ PR #44 的 20261123-01）

- **顺序**：先迁移、后合并。`20261123-01` 给 `user` 表加 3 列（`public_uid` / `bio` / `profile_visibility`）和唯一索引 `uk_user_public_uid`，并同步 `avatar` 的列注释。PR #44 合并会自动部署，新代码一上线就要读这些列，所以迁移必须在前。
- **迁移前核对**：`user` 表 9 列、没有 `uk_user_public_uid`（确认没迁过）、14 个用户，`avatar` 的类型和默认值与迁移脚本预期的基线一致；按运维手册跑手工备份，得到 `/opt/se2026/backups/mysql/se2026-20261126-184026.sql.gz`。
- **脚本怎么到服务器上**：合并前服务器上还没有这个文件。本地把 PR 头上的脚本转成 base64、按 200 字符切段，每段一条短命令追加到 `/tmp`；服务器上 `base64 -d` 还原后比对 md5（`025a95e0…`，与仓库里的文件一致）。
- **命令**：`P=$(sudo docker exec se2026-mysql sh -c 'printf %s "$MYSQL_ROOT_PASSWORD"') && sudo docker exec -e MYSQL_PWD="$P" -i se2026-mysql mysql --default-character-set=utf8mb4 -uroot se2026 < /tmp/se2026-mig-20261123-01.sql`。密码取自容器自带的环境变量，不经过本机；命令前加了「`user` 表仍是 9 列才执行」的保护。
- **结果**：**零错误执行完毕**（mysql 退出码 0，输出里没有任何 ERROR）。
- **迁移后核对**（逐项都过了）：12 列，顺序是 `… email → public_uid → bio → profile_visibility → created_at …`；`uk_user_public_uid` 唯一索引在；14 个用户不变，`public_uid` 全为 NULL（脚本不回填，存量用户首次登录时由应用层补分配）；各列的中文注释读回是正确的 UTF-8；`SHOW CREATE TABLE user` 与全新安装的定义逐行比对，列名、类型、可空、默认值、键、表选项和各列注释都一致。唯一不同的是 `username` / `password_hash` / `nickname` / `email` 四个老列多显示一个 `CHARACTER SET utf8mb4` 标注——生产库建表时留下的，语义无差，与这次迁移无关。
- **上线闭环**：迁移后先确认旧代码读新表正常（不存在的账号登录返回 401，不是 500），再合并 PR #44。部署后健康检查通过；`/api/v1/users/me`、`/api/v1/friends` 未登录返回 401（路由在）；用开发令牌按一个不存在的 UID 查人返回 404「该 UID 不存在」（新代码读得到 `public_uid`）。没有用真实账号登录，「登录时补分配 UID」在线上还没实际触发过。
