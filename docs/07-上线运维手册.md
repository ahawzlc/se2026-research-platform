## 二、运行拓扑

```
公网 80
  └─> web 容器（Nginx：托管前端产物 + 反代 /api/）
        └─> backend 容器（NestJS，8080，仅容器网络）
              └─> mysql 容器（MySQL 8.0，3306，仅容器网络）
```

- **只有 web 映射宿主机 80**。MySQL 与后端不对外暴露端口，数据库无法从公网直连（避免被扫库）。
- 三个容器在同一 bridge 网络 `se2026-net` 内，互相用服务名访问（`mysql`、`backend`）。
- 数据卷：`se2026-prod-mysql-data`（数据库）、`se2026-prod-uploads`（上传文件，挂到容器 `/data/uploads`）。
- `restart: unless-stopped`，且 `docker` 服务已 `systemctl enable`，服务器重启后自动恢复。

## 三、日常命令

所有命令先 `cd /opt/se2026/deploy`。

```bash
# 查看状态（三容器是否 healthy）
docker compose -f docker-compose.prod.yml --env-file .env.prod ps

# 看日志
docker compose -f docker-compose.prod.yml --env-file .env.prod logs -f backend
docker compose -f docker-compose.prod.yml --env-file .env.prod logs --tail=100 web

# 重启单个服务（改了环境变量后必须 up -d 才会生效，restart 不读新 .env）
docker compose -f docker-compose.prod.yml --env-file .env.prod restart backend

# 进入数据库
docker exec -it se2026-mysql mysql -uroot -p se2026

# 查看表
docker exec -e MYSQL_PWD=<root密码> se2026-mysql mysql -uroot -N -B \
  -e "SELECT table_name FROM information_schema.tables WHERE table_schema='se2026';"

# 磁盘与内存
df -h /; free -h; docker system df
```

## 四、发版流程

### 方式一：服务器上手工发版（当前默认）

代码更新后，从本地把 `backend/ frontend/ deploy/` 传到服务器，再执行部署脚本：

```bash
# 本地（仓库根目录）——只传需要的目录，排除依赖与产物
tar -czf /tmp/release.tgz --exclude='.git' backend frontend deploy
scp /tmp/release.tgz ubuntu@82.156.156.94:/tmp/release.tgz

# 服务器上
tar -xzf /tmp/release.tgz -C /opt/se2026
chmod +x /opt/se2026/deploy/scripts/*.sh
/opt/se2026/deploy/scripts/deploy.sh
```

`deploy.sh` 做的事：compose 配置校验 → 构建 backend/web 镜像 → `up -d` 滚动重建 → 轮询健康检查（默认 180s）→ 打印容器状态。**不碰数据库卷，不覆盖 `.env.prod`**。失败时自动打印最近日志并以非 0 退出。

依赖变更（改了 `package.json`）后建议加 `--no-cache`：

```bash
/opt/se2026/deploy/scripts/deploy.sh --no-cache
```

### 方式二：GitHub Actions 自动部署（已就绪，需一次性配置）

`.github/workflows/deploy.yml` 已写好：push 到 `develop` 或手动触发时，runner 打包 → scp → ssh 执行 `deploy.sh` → 公网健康检查。

一次性配置（在服务器上生成部署专用密钥，密码登录不用于 CI）：

```bash
# 服务器上执行
ssh-keygen -t ed25519 -N '' -C 'github-actions-deploy' -f ~/.ssh/deploy_ed25519
cat ~/.ssh/deploy_ed25519.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys ~/.ssh/deploy_ed25519
ssh-keyscan -p 22 82.156.156.94 2>/dev/null > ~/.ssh/deploy_known_hosts
```

然后在 GitHub 仓库 **Settings → Secrets and variables → Actions → New repository secret** 填入 5 项：

| Secret | 值 |
| --- | --- |
| `DEPLOY_HOST` | `82.156.156.94` |
| `DEPLOY_PORT` | `22` |
| `DEPLOY_USER` | `ubuntu` |
| `DEPLOY_SSH_KEY` | `~/.ssh/deploy_ed25519` 的**完整内容**（含 `-----BEGIN` 与 `-----END` 行） |
| `DEPLOY_KNOWN_HOSTS` | `~/.ssh/deploy_known_hosts` 的完整内容 |

> 私钥只存在于服务器与 GitHub Secrets，不写入仓库、不贴在聊天里。
> 仓库为公开库，Actions 在公开库上运行**不会**把 Secrets 暴露给 fork 的 PR。

## 五、备份与恢复

### 自动备份

`crontab -l` 已配置：

```
30 3 * * * /opt/se2026/deploy/scripts/backup-mysql.sh >> /opt/se2026/backups/backup.log 2>&1
```

- 每天 03:30 执行，`mysqldump --single-transaction` 一致性快照，不锁表；
- gzip 压缩 + 完整性校验 + 最小体积校验（防止 dump 失败留下空文件）；
- 自动删除超过 7 天的备份；日志在 `/opt/se2026/backups/backup.log`。

手工立即备份：

```bash
/opt/se2026/deploy/scripts/backup-mysql.sh
ls -lh /opt/se2026/backups/mysql/
```

### 恢复

```bash
# 1) 演练：只校验文件完整性与建表语句数，不写库
/opt/se2026/deploy/scripts/restore-mysql.sh /opt/se2026/backups/mysql/se2026-20261030-033000.sql.gz

# 2) 真正恢复：会自动先备份当前数据，再覆盖
/opt/se2026/deploy/scripts/restore-mysql.sh /opt/se2026/backups/mysql/se2026-20261030-033000.sql.gz --yes
```

### 备份要拷走

服务器上的备份不能当唯一副本（机器挂了就全没了）。演示前一天建议把最新的 `.sql.gz` 拉到本地一份：

```bash
scp ubuntu@82.156.156.94:/opt/se2026/backups/mysql/<最新文件>.sql.gz ./
```

## 六、排障

| 现象 | 检查 | 处理 |
| --- | --- | --- |
| 浏览器打不开首页 | `docker compose ps` 是否 `healthy` | 非 healthy 看 `logs web`；全正常则查腾讯云安全组是否放行 80 |
| `/api/v1/health` 返回 `database: disconnected` | `docker compose ps` 中 mysql 状态 | mysql 未 healthy 时后端会连不上，等其恢复或 `restart backend` |
| 部署后仍是旧页面 | 浏览器缓存 | 已对 `index.html` 设 `no-cache`；强刷 Ctrl+F5 |
| 容器反复重启 | `docker compose logs --tail=100 backend` | 多为 `DATABASE_URL` / `JWT_SECRET` 缺失或 `.env.prod` 拼写错误 |
| 接口时间差 8 小时 | MySQL `default-time-zone` 是否被改 | 必须保持 `+00:00`，对外时间由 `formatDateTime()` 转北京时间 |
| 构建很慢或失败 | `docker system df` 看磁盘 | `docker builder prune -f` 清构建缓存；磁盘不足时清 `docker image prune -a` |
| 忘记数据库密码 | `sudo grep MYSQL_PASSWORD /opt/se2026/deploy/.env.prod` | 该值即应用账号密码 |

## 七、安全注意

1. **`deploy/.env.prod` 绝不入库**（`.gitignore` 已覆盖 `.env.*`），也不要贴到群里或文档里。
2. **演示期 `APP_ENABLE_DEV_TOKEN=true`**：任何人可调用 `/api/v1/auth/dev-token` 签发令牌。A 组登录接口上线、且演示结束后，应改为 `false` 并 `up -d` 生效。
3. 只有 80 端口对外；**不要**为了图方便把 3306 映射到宿主机。
4. 数据库密码与 `JWT_SECRET` 由 `openssl rand` 生成，若怀疑泄露，改 `.env.prod` 后 `up -d`（改 `JWT_SECRET` 会让已签发令牌全部失效）。
5. 服务器仅开放 22 + 80；如后续加域名与 HTTPS，走 443 并在 Nginx 配置证书。

## 八、资源现状

2 核 3.6 GB 的机器同时跑 MySQL + Node + Nginx，已做过针对性限制：

- MySQL：`--innodb-buffer-pool-size=256M`、`--max-connections=100`；
- Docker 日志：单文件 20 MB × 3 个（`/etc/docker/daemon.json`），防止日志写满磁盘；
- 当前占用：磁盘 88 GB 用约 6 GB，内存常驻约 1.2 GB。

若后续要加 Redis 或做压测，先 `free -h` 确认余量；内存吃紧时优先给 MySQL 降 buffer pool，而不是加 swap。
