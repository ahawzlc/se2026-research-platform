## 三、关键决策与备选方案

> 均逐条对照 `docs/01`、`docs/02`、`docs/03`、`docs/12` 后确定；被否决的方案附理由，便于答辩时说明取舍。

### 决策 1：接口与 docs/12「接口方向」的四处出入

docs/12 写的是方向性草案，`docs/01` 才是冻结契约，所以先改 `docs/01` 再写代码（两个 docs 提交都排在对应代码之前）。

| # | docs/12 原文 | 实际落地 | 理由 |
| --- | --- | --- | --- |
| ① | `PATCH /community/posts/:id` | `PUT` | 前端 `http` 封装没有 PATCH；项目 / 文献 / 会议的更新接口全是 PUT |
| ② | `tag=` | `tags=1,6`（命中任一） | 任务卡要求「标签多选」，单值参数表达不了 |
| ③ | 未列出停止招募接口 | 补 `POST /posts/:id/close` | 任务卡要求发帖人可「停止招募」 |
| ④ | 未列出「只看我的」 | 列表加 `mine=true` | 任务卡要求「管理自己的帖子」，没有入口就只能翻页找 |

**备选**：给前端 `http` 补 PATCH 方法以迁就 docs/12 —— 否决。为一个接口改动全站请求封装，不如与其余更新接口保持一致。

### 决策 2：帖子是跨组公开内容，权限按「作者本人」判断

红线 9 要求「查询必须带团队归属条件」，但社区帖子发帖时**不属于任何课题组**（`community_post.team_id` 为空），
没法套用 `team_member` 校验。本线的归属条件即「发帖人」：读对全站登录用户开放，改 / 删 / 审批在 service 层比对 `post.userId === 当前用户`。
非作者一律 403，不存在 / 已删除 / id 非法一律 404（不泄露存在性）。

发布人卡片**只返回昵称与头像**，不带登录名和邮箱——全站可见的内容应遵循最小披露（会议纪要强调的隐私原则）。

### 决策 3：名额用「条件更新」扣减，防并发超招

任务卡明确要求「并发下不能超招」。通过申请时在事务内执行：

```ts
// 只有仍有名额（且帖子未删、仍处于 recruiting / closed）才会 +1；否则影响行数为 0
updateMany({ where: { id, deleted: 0, status: { in: ['recruiting','closed'] }, recruitedCount: { lt: recruitTotal } },
             data: { recruitedCount: { increment: 1 } } })
```

同一条申请也先做一次「原子占位」（`where: { id, status: 'pending' }`），两个请求并发审批同一条申请时只有一个生效。

| 方案 | 结论 |
| --- | --- |
| **条件更新**（采用） | 一条语句完成判断与扣减，不依赖隔离级别，也不需要显式加锁 |
| 事务内先 `SELECT … FOR UPDATE` 再读计数 | 名额扣减不用它（要写原生 SQL，且必须保证锁前没有建立快照的一致性读）。**评审后局部改用**：事务开头锁住帖子行并回读「是否已绑定课题组」，名额仍是条件更新——原因见第九节 9.2 第 1 点 |
| 事务内重查计数再 `increment`（docs/12 原文「事务内重查计数」） | **否决**：查与改之间仍有窗口。真库用例做过变异验证——换成这种写法，「并发审批不超招」用例立刻变红（见第四节） |

### 决策 4：通过申请是一个事务，通知也在其中

任务卡要求「通过动作用事务」。事务内依次：申请占位 → 锁定帖子并回读 → 未绑定课题组则自动建组并绑定 → 申请人入组 →
新增了成员才名额 +1 → 达到招募人数转 `full` → 写通知。任一步失败整体回滚，不会出现「加了名额但人没进组」或「进了组但没通知」。
（首版的顺序是「占位 → 名额 → 建组 → 入组」，评审后调整，见第九节 9.2。）

通知写入走 `NotificationsService.pushInTransaction(tx, …)`，**不绕过 NotificationsService 直写 `notification` 表**
（docs/02：唯一写入口是 push）。`push` 的冻结签名原样不动。

**备选**：事务提交后再调 `push` —— 否决。进程在两步之间崩溃会丢通知，与任务卡的原子性要求不符。

### 决策 5：复用课题组模块，而不是复制一套建组逻辑

任务卡要求「建 Team（复用现有 teams 模块逻辑）」。`TeamsService.createTeam` 自己开事务、自己重试邀请码，无法嵌进调用方的事务。
把事务体抽成 `createTeamInTransaction(tx, …)`，`createTeam` 改为调用它——对外行为不变（原单测未改动即通过）。

| 方案 | 结论 |
| --- | --- |
| 抽公共方法（采用） | 建组规则只有一份；对 teams 模块是纯增量 |
| 在社区模块里重写建组与邀请码生成 | **否决**：邀请码字母表、重试上限、组长记录会出现两份，日后必然漂移 |
| 把 `TeamsModule` 的表操作搬到 common 层 | **否决**：改动面过大，越出本卡范围 |

`ensureMemberInTransaction` 与 `join` 的差别：已是成员时**不报错**（申请人可能已凭邀请码先入组）；曾退出的成员恢复原行
（`uk_team_member` 不过滤软删行，不能新增）。评审后它改为返回「本次是否真的新增了一名成员」，审批据此决定是否占名额（9.2）。

### 决策 6：已停止的帖子仍可处理存量申请

任务卡：「停止招募 / 删帖后……已存在的 pending 申请在发帖人申请管理页仍可见可处理（简化口径，会上可改）」。

- **停止招募**：不再接新申请（409），存量待处理申请在名额内仍可通过；通过后帖子**保持 `closed`**，不会因名额占满改成 `full`
  （「停止」是发帖人的明确意图，系统不应覆盖）。
- **删帖**：见决策 7。

### 决策 7：还有待处理申请时不允许删帖（409）——**请复核**

任务卡同一句话把「停止招募」和「删帖」并列，说两者的存量申请都「仍可见可处理」。但删帖后「广场与详情立即不可见」，
申请人列表挂在详情页里，发帖人**根本进不去**——两条要求在「删帖」上互相矛盾，只能二选一。

| 方案 | 结论 |
| --- | --- |
| 有 `pending` 申请时禁止删除，提示「还有 N 条待处理申请，请先处理后再删除」（采用） | 不产生孤儿申请；每个申请人都能等到结果 |
| 允许删除，存量申请随帖子一起不可达 | **否决**：申请永远停在「待处理」，申请人等不到任何通知 |
| 允许删除，但自动把存量申请全部置为拒绝并通知 | 否决：代替发帖人做了拒绝的决定 |

任务卡自己标注了「简化口径，会上可改」，这条按「请复核」处理（第五节第 2 点）。若全组倾向其他方案，改动只在 `remove()` 一处。

### 决策 8：自动建组后，邀请码随审批响应给出一次

`POST /teams` 的约定是「邀请码只在建组时给出一次」。自动建组时如果不同样交还给组长，这个课题组的邀请码就**永远没人见过**，
组长想线下拉人（决策点 2：「邀请码保留给线下拉人」）将无从下手。所以通过响应里带 `inviteCode`，前端弹一次性展示（与
「课题组成员」页建组后的展示同一口径）；课题组已存在时不返回。

### 决策 9：广场筛选随 URL 保存

广场是「浏览 → 进详情 → 返回」的高频动线。筛选条件写进 `?tags=&q=&status=&mine=`，从详情返回或带参直达都能还原。
其余页面的筛选不进 URL，这里是有意为之的差异。

### 决策 10：「申请管理」做成详情页里的页签

任务卡原文是「帖子详情的『申请管理』页签」。页签状态同样随 URL（`?tab=applications`），铃铛的「有人申请」通知直达该页签。

**备选**：抽屉（与项目 / 任务详情抽屉一致）——否决，任务卡写明是页签，且抽屉里放分页表格偏挤。

### 决策 11：「私信 TA」的跨线接缝

任务卡 E-1 要求发布人卡片上有「私信 TA」按钮，但「打开或新建与该用户的私信会话」属线③ E-3。约定：

- 按钮 → `/messages?peer=<userId>`；
- 消息页读到 `peer` 后调用**现有的** `conversationsApi.ensurePrivateConversation(peer)` 打开（或新建）会话。打开本身幂等，
  所以不刻意清除 URL 参数：刷新页面只是重新定位到同一个会话，不会多建。

这样线③ 换后端实现（放宽同组限制或改用 `private-with` 接口）时，本线代码不用动。**现状**：后端仍要求双方同组，
不同组的发布人会被拦下并提示「对方不在你的课题组中」——等线③ E-3 落地后自然打通（线③ 的 PR #44 正在解除同组限制）。

**备选**：把原「私信」弹窗的打开逻辑抽成公共函数供两处共用——第一版就是这么做的，后来撤回（提交 `ff4a0b2`）。线③ 的 PR #44
恰好在改同一个 `handlePrivateCreate`，重构别人的功能函数只会给对方制造合并冲突，而省下的不过是 4 行重复代码。
现在本线对 `MessagesView.vue` 的改动是**纯新增**（+21 / −0）。

## 六、排坑记录（给其他线，均在本线实际踩到）

**后端 / 测试**

1. `npm run lint` 带 `--fix`，会重排文件；之后 **ESLint 报的行号是修复前的坐标**，对不上就单独跑 `npx eslint <file>`（不带 `--fix`）。
2. `res.body` 是 `any`：在 e2e 里直接 `res.body.code` 会触发 `no-unsafe-assignment` / `no-unsafe-member-access`。
   照既有 e2e 的写法用 `envelope<T>(res)` 收窄类型。
3. Jest 的 `expect.any()` / `expect.stringContaining()` / `expect.objectContaining()` 返回 `any`：**放进对象字面量**（哪怕是作为参数传入）
   会触发 `no-unsafe-assignment`。要断言调用参数时，给替身标上签名再读实参：`jest.fn<Promise<T>, [Args]>()`（本机 `@types/jest` 的
   `jest.fn` 泛型是「<返回类型, 参数元组>」，返回类型要写成 Promise，`mockResolvedValue` 才有类型）。
4. Prisma 直接写外键列时，类型用 `XxxUncheckedCreateInput`（`XxxCreateInput` 要求用关系写法）。
5. 手写的事务替身传给 service 时需要 `as unknown as Prisma.TransactionClient`。
6. `@Transform(({ value }) => …)` 的回调参数要显式标注 `unknown`，否则 lint 报 `no-unsafe-return`（线①在 Issue #42 修过同一问题）。
7. supertest：请求头必须设在具体的 `.get()/.post()` 实例上，设在 `request(server)` 工厂上不会带到真正发出的请求；
   `waitForURL` 只接受字符串通配符，不接受正则。

**前端**

8. `el-tag` 自带缩放离场动画：从 `v-for` 里移除一个标签后，它的 DOM 节点会**再存在约 300ms** 才被摘掉。写依赖 DOM 数量的断言或
   自动化脚本时要等动画结束；后台标签页里动画会被节流，持续更久。
9. 同理，`el-dialog` / `ElMessageBox` 关闭后节点仍在 DOM 里（隐藏）。按文案定位按钮时要把范围限定到当前可见的容器，否则会命中上一次关闭的那个。

**浏览器自动化（IAB）**

10. 坐标点击与按键事件的送达不可靠（docs/12 已记录）。验证页面逻辑时，直接在元素上派发 `click` / `keyup` 更稳——走的仍是组件真实的事件处理。
11. DOM 刚变化时立刻截图可能拿到未绘制完的半成品帧（本线第一次截卡片时标签全是空白，实际 DOM 与样式是对的）。截图前先等页面稳定。

### 9.1 CI「真库集成测试」间歇性 P2034：测试文件并行 + 物理删父行

**现象**：[run 45354929190](https://github.com/ahawzlc/se2026-research-platform/actions/runs/45354929190) 首次执行时，
社区套件的审批在 `tx.notification.create` 报 P2034（MySQL 死锁），重跑即绿。日志里报错与认证套件收尾只差 8 毫秒。

**等待环**：本地按 CI 的方式（三个套件并行、每轮全新库）重跑 60 轮，复现 2 次，InnoDB 记下的原文（去掉记录字段）：

```text
(1) TRANSACTION  DELETE FROM `user` WHERE `user`.`username` LIKE 't1a_%'          ← 认证套件 afterAll 的清理
    持有  notification.idx_notification_user_read 末尾的共享锁（supremum：索引末尾的间隙）
    等待  user.PRIMARY  lock_mode X locks rec but not gap                            ← 发帖人 t2c_a_… 那一行

(2) TRANSACTION  INSERT INTO `notification` (…, 5, 'team_apply_approved', …)      ← 社区套件的审批事务
    持有  user.PRIMARY  lock mode S locks rec but not gap（发帖人、申请人两行）
    等待  notification.idx_notification_user_read  lock_mode X insert intention

WE ROLL BACK TRANSACTION (2)
```

| | 认证套件 `afterAll` | 社区套件的审批事务 |
| --- | --- | --- |
| 语句 | `DELETE FROM user WHERE username LIKE 't1a_%'` | `INSERT INTO notification (…)`（另一轮是 `INSERT INTO team_member`） |
| 持有 | 子表外键索引末尾的**共享间隙锁**——删 `user` 父行时逐张检查子表外键留下的 | 发帖人、申请人两行 `user` 主键上的**共享锁**——建组 / 入组 / 写通知的外键检查留下的 |
| 等待 | `user` 主键上的排他锁——范围扫描读到用户名排在 `t1a_` 之后的第一条用户，正是社区套件的发帖人 | 同一子表索引末尾的**插入意向锁**——要往那个间隙里插一行 |

两边互等，InnoDB 回滚其中一方，两次都是审批事务，与 CI 上的报错位置一致。审批事务是原子的，回滚后没有留下半截数据。

**结论**：是测试之间互相干扰，不是审批事务在并发下有问题。成环的两个必要条件是「物理删除 `user` 父行」与「往 `user` 的子表插入」
并发；业务代码里没有任何物理删除用户的路径（`backend/src` 里唯一的 `delete` 是登录限流器清理内存计数）。

**对照**：只让审批事务并发、没有任何清理——6 帖 × 6 人 × 30 轮共 1080 笔审批同时发出（同帖抢名额、不同帖同时首次建组），
InnoDB 死锁计数不变。修复前的审批代码在这一组里同样 0 死锁，说明评审人担心的「审批事务本身在并发下有问题」不在死锁上，
而在下面 9.2 第 1 点。

**处理**：`backend/test/jest-integration.json` 加 `maxWorkers: 1`，三个套件串行执行。这是卡 T-1a 的测试基建，线②代改，

### 9.2 排查中发现并修掉的三个问题

都在审批事务里，真库用例先红后绿。

1. **并发首次通过会重复建组**。原实现用事务外读到的 `post.teamId` 判断「是否已绑定课题组」：名额 ≥ 2 时两笔首次通过并发，
   两笔都读到空，各建一个课题组，帖子最后绑到后提交的那个——先入组的人落在一个没人绑定的课题组里。
   对照压测里 180 个帖子全部中招（每帖 3 个课题组、绑定的组里只有 2 人）。名额没有超招，所以既有用例没发现。
   修法：事务开头先 `SELECT … FOR UPDATE` 锁定帖子行并回读，名额、状态、课题组绑定都以持锁后的已提交数据为准，
   同一帖子的审批从这里排队。Prisma 的模型查询带不了 `FOR UPDATE`，这是本线唯一一处原生 SQL。
2. **评审补修留了一条路径**：申请人先申请、等待期间凭邀请码入组、再被通过。`a7c6d5b` 拦的是「已入组后再申请」。
   原实现照样 `recruited_count +1`，帖子满员后这条存量申请还会被 409 拦下。修法：`ensureMemberInTransaction` 返回
   「本次是否真的新增了成员」，只有新增才占名额；已是成员的申请照常通过并通知，帖子不变（已满员也照常通过）。
   docs/01 补了这条口径；`01-schema.sql` 里 `recruited_count` 的列注释「每审批通过一人 +1」没有动（表结构冻结）。
3. **审批与邀请码入组撞到同一申请人时返回 500**。审批事务里「查不到成员行 → 插入」之间，申请人恰好凭邀请码入了组，
   插入撞 `uk_team_member`，原样抛出。修法同上：以唯一索引的结论为准，落败时不占名额。

新增用例见 docs/14 的「E-2 评审回应」一行。单测里把回读换回事务外快照，「并发首次通过」一例即失败（变异验证）。
