## 三、关键决策与备选方案（本 PR）

> 以下决策均由 B 组同学在 AI 辅助梳理出的候选方案基础上**逐条比对 `docs/01` / `docs/02` / `docs/03` 后拍板确定**，并对被否决的方案给出理由，便于答辩时说明取舍逻辑。

### 决策 1：里程碑埋点的幂等与撤销语义

按 `docs/03` 的防刷口径实现：

| 埋点 | 权重 | 幂等键 | 撤销行为 |
| --- | --- | --- | --- |
| `milestone_done` | 2.5 | `userId + milestoneId` | 里程碑从 `done` 退回 `pending` 时，权重置 0 |

- **实现要点**：`recordOnce` 判断「是否已存在**有效**埋点」时用 `weight > 0` 而不是「是否存在记录」。原因：撤销是**软撤销**（权重置 0 而不是删行），如果只看「有没有记录」，一个被撤销的里程碑重新完成时就无法再次计分（踩过一次坑，已修复并有回归断言）。
- **备选方案**：直接删行撤销 —— 已否决。`activity_log` 是「只增不改」的流水表，删行会丢失「曾经完成过又撤回」的可追溯信息。

### 决策 2：所有查询强制带团队标识（红线 9）

- **做法**：抽 `requireTeamMembership` / `listUserTeamIds` 到 `common/team-access.ts`，项目、里程碑的**每一个**查询都在 `where` 里带 `teamId`。
- **实测**：未入组的用户 C 读取项目列表 → 看不到；读取项目详情 → 403。已写进 e2e 断言。

### 决策 3：看板排序用整数间隔（step 100），取中点

- **依据**：`docs/02` 的任务表 `sort_order` 字段说明与 `docs/01` 的排序约定。
- **做法**：新任务 `sort_order = 上一条 + 100`；拖到两项之间时取 `floor((前邻居 + 后邻居) / 2)`；拖到列首/列尾时取 `后邻居 - 100` / `前邻居 + 100`。
- **兜底**：当中值小于最小间隔（说明间隔已被反复插入耗尽）时，后端对该列整体重排为 100、200、300……
- **被移动任务在重排时的位置**：重排不是简单地按旧顺序重写，而是把被移动的任务插到 `afterSortOrder` 给出的邻居之前（即列首），保证拖拽意图不丢失。
- **备选方案**：
  - *用小数（float）* —— 已否决。浮点数排序在 MySQL 里精度不稳定，且不便于人工排查；
  - *每次拖动都整体重排列* —— 已否决。写放大严重，多人同时拖拽时冲突概率高。

### 决策 4：`task_done` 的幂等键

按 `docs/03` 的防刷口径：

| 埋点 | 权重 | 幂等键 | 撤销行为 |
| --- | --- | --- | --- |
| `task_create` | 3.0 | 无（每次创建都记） | — |
| `task_done` | 3.0 | `userId + taskId` | 任务从 `done` 退回其它状态时，权重置 0 |

- **关键点**：`task_done` 的幂等键**包含 `taskId`**，所以「把 3 个不同任务各拖到 done」算 3 次分，但「把同一个任务反复拖到 done」只算 1 次。
- **实测**：done → doing → done → done 连续三次，最终只记 1 条有效埋点；退回 doing 时权重归零，再次 done 重新计 1 次。已写进 e2e 断言。

### 决策 5：前端看板用 `vuedraggable` 的 `change` 事件，而不是 `add` / `update`

- **踩坑与修复**：最初按 vuedraggable 常见写法绑了 `@add` / `@update`，结果拖拽后后端完全没被调用。查 `node_modules/vuedraggable/src/vuedraggable.js` 源码后确认：
  - `add` / `update` 拿到的是 **Sortable 原始事件**，`evt.item` 只是一个 DOM 节点，拿不到任务的 `id`；
  - `change` 事件才是 vuedraggable **归一化过**的载荷，形如 `{ added: { element, newIndex } }` / `{ removed: {...} }` / `{ moved: {...} }`，其中 `element` 就是数组里的那个任务对象（含 `id`、`sortOrder`）。
- **最终做法**：统一用 `@change="handleColumnChange(column.key, $event)"`，按 `added` / `moved` 分支处理；`removed` 不处理（跨列拖拽由目标列的 `added` 分支负责改状态与落库）。
- **额外收获**：`change` 同时覆盖跨列与同列两种场景，不必再分别维护 `add` 与 `update` 两套逻辑。

### 决策 6：任务评论复用 `conversation` + `message`，不新建 `task_comment` 表

- **依据**：`docs/02` 的表结构里没有独立的 `task_comment` 表，而有 `conversation`（`type` / `ref_type` / `ref_id`）与 `message` 两张通用表。
- **做法**：任务评论落成 `conversation(type='comment', ref_type='task', ref_id=taskId)` 下的 `message` 记录。
- **备选方案**：新建 `task_comment` 表 —— 已否决。理由：一是与 `docs/02` 冻结的数据字典冲突（改表要走三步走流程）；二是后续 C-5 协作消息与 B-补1 项目讨论区同样需要会话模型，新建独立表会造成三套重复实现。
- **额外收益**：`ConversationsService` 抽成公共模块后，C 组做 C-5 时可直接复用，不需要二次返工。

### 决策 7：`comment_create` 的单日上限（防刷不等于禁言）

- **依据**：`docs/03` 的反刷分设计要求评论计入参与度时有上限。
- **做法**：同一成员单日计入上限 **10 条**。超过上限后**评论仍然可以正常发表**，只是不再计入统计 —— 避免把「防刷」做成「不许发言」。
- **备选方案**：超限直接拒绝发言 —— 已否决。防刷的目标是防止刷分，不是剥夺讨论权；直接拒绝会让用户以为系统坏了。

### 决策 8：甘特图的日期来源

- **现实约束**：`docs/02` 的 `milestone` 表只有 `due_date` 一个日期字段，没有起止日期。
- **做法**：里程碑的「开始日期」取**项目开始日期**，「结束日期」取里程碑截止日期，因此同一项目的多个里程碑呈现为「项目起点 → 各截止点」的阶梯形状。
- **备选方案**：给 `milestone` 加 `start_date` 字段 —— 已否决，改表要走 `docs/02 → 01-schema.sql → schema.prisma` 三步走流程，需要全组确认，超出本次任务卡范围。若全组认为阶梯形状不够用，可另开一张卡加字段。

2. 删 `conversation` 前先删 `conversation_member`，删 `team` 前先删 `activity_log` / `literature` / `team_member`。
