## 三、关键决策与备选方案（本 PR）

> 以下决策均由 B 组同学在 AI 辅助梳理出的候选方案基础上**逐条比对 `docs/01` / `docs/02` / `docs/03` 后拍板确定**，并对被否决的方案给出理由，便于答辩时说明取舍逻辑。

### 决策 1：里程碑埋点的幂等与撤销语义

按 `docs/03` 的防刷口径实现：

| 埋点 | 权重 | 幂等键 | 撤销行为 |
| --- | --- | --- | --- |
| `milestone_done` | 2.5 | `userId + milestoneId` | 里程碑从 `done` 退回 `pending` 时，权重置 0 |

- **实现要点**：`recordOnce` 判断「是否已存在**有效**埋点」时用 `weight > 0` 而不是「是否存在记录」。原因：撤销是**软撤销**（权重置 0 而不是删行），如果只看「有没有记录」，一个被撤销的里程碑重新完成时就无法再次计分（踩过一次坑，已修复并有回归断言）。
- **备选方案**：直接删行撤销 —— 已否决。`activity_log` 是「只增不改」的流水表，删行会丢失「曾经完成过又撤回」的可追溯信息。

### 决策 2：所有查询强制带团队标识（红线 9）

- **做法**：抽 `requireTeamMembership` / `listUserTeamIds` 到 `common/team-access.ts`，项目、里程碑的**每一个**查询都在 `where` 里带 `teamId`。
- **实测**：未入组的用户 C 读取项目列表 → 看不到；读取项目详情 → 403。已写进 e2e 断言。

### 决策 3：甘特图的日期来源

- **现实约束**：`docs/02` 的 `milestone` 表只有 `due_date` 一个日期字段，没有起止日期。
- **做法**：里程碑的「开始日期」取**项目开始日期**，「结束日期」取里程碑截止日期，因此同一项目的多个里程碑呈现为「项目起点 → 各截止点」的阶梯形状。
- **备选方案**：给 `milestone` 加 `start_date` 字段 —— 已否决，改表要走 `docs/02 → 01-schema.sql → schema.prisma` 三步走流程，需要全组确认，超出本次任务卡范围。若全组认为阶梯形状不够用，可另开一张卡加字段。
